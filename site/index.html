The problem

A Stellar address does not say what the receiver needs.

The exchange needed a memo

Exchanges keep everyone's deposits in one account and tell them apart by the memo. Send without it and the money arrives, but nobody knows it is yours. Most exchanges never mark their accounts as needing one, so a wallet cannot always warn you. Stellagate checks the account itself, and a public list of more than a hundred accounts known to need one.

The wallet could not hold the asset

A Stellar account has to opt in to each asset before it can receive it, and the issuer sometimes has to approve it too. Send USDC to a wallet that has not opted in and the payment fails. Stellagate checks before you sign.

A smart wallet cannot add a memo

Passkey wallets pay through smart contracts, and those payments have no memo field. Sending from one to an exchange that needs a memo is likely to go missing. Stellagate tells you to send from a regular account instead, or to use the exchange's M-address if it offers one.

Research

The memo gap

87%

of memo-required exchange accounts do not set the SEP-29 flag on chain.

Most exchanges never set it. A survey of 107 pooled deposit accounts tagged as memo-required across the public directory showed that 93 major services, including Binance, Kraken, Bitstamp, and Coinbase Deposits, never configure the SEP-29 flag on chain. Funds sit uncredited. A wallet checking only the on-chain flag misses almost all of them. Stellagate combines SEP-29 on-chain data, the public directory, and SEP-2 federation lookup into a single send-time check.

Architecture

How it works

Address parsing and safety checks

Stellagate accepts raw destination strings: classic accounts (G...), muxed addresses (M...), Soroban contracts (C...), and SEP-2 federation names (user*domain.com). Muxed IDs are unpacked into base accounts. Pasted secret keys are refused immediately and never reach a network request or the URL.

Direct network and directory verification

The library queries Horizon, Stellar RPC, and directory records in parallel. It inspects SEP-29 account flags, directory memo tags, classic asset trustline authorization and limits, Soroban Stellar Asset Contract deployments, and contract-sender compatibility.

Standardised verdict and actionable fix

Returns a simple status: block, warn, or ok. If blocked, you get a machine-readable reason code, a plain-language explanation, and the exact corrective action to present to your user.

Empirical proof

Verified on testnet

We ran each scenario through Stellagate, and then we attempted the payment on the network anyway. Every block verdict matched a payment the network refused. That is the point. The one exception is an uninitialised contract address, where the network accepted the transfer and left the tokens stranded. Stellagate blocks that before you send.

Integration

For wallet and dapp developers

Run the check before transaction building. Stellagate returns a status, machine-readable reason codes, and plain-language fixes you can present directly in your send flow.

TypeScript 
import { check } from "@stellagate/core";

const verdict = await check({
  to: "GABFQIK63R2NETJM7T673EAMZN4RJLLGP3OFUEJU5SZVTGWUKULZJNL6",
  from: "CC2BO6ZMFVILIJVGW777H3HB4GUKWQ7E5Y4NODWJXTIJBDKHLKPWSN4C",
  asset: "native",
  network: "public",
});

if (verdict.status === "block") {
  // Stop flow and show verdict.reasons[0].message and .fix
}
block

Stop the payment when blocked. The transaction will fail on chain, or arrive at a pooled exchange account where funds cannot be credited.

warn

Confirm on warnings. The account needs funding first, or a contract is paying a muxed address that some exchanges do not credit yet.

ok

Safe to proceed. Destination exists, memo requirements are met, and the address can hold the asset.
